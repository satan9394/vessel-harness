## 0. 核心定位与技术愿景

随着 Agent 进入工业级复杂长流程与多 Agent 协同阶段，两大核心瓶颈制约了系统的持久运行：
1. **上下文与内存膨胀危机**：
   - 传统定比截断（如单纯以 `0.8 * contextWindow`）未能考虑大输出空间（Max Output Tokens）与 CJK 词元膨胀（~1.3x），导致主动压缩触发线压在上游真实物理墙之上，造成长会话 100% 打爆遭遇 HTTP 400 崩溃；
   - 本地 MCP 进程由于缺乏内核级收尸与按需加载机制，在多次服务 reload 或热重载时派生大量孤儿孙进程（实测曾占用 2.7GB 内存）；
2. **多 Agent 协同漂移与缺乏预审**：
   - 异步团队在队长或全局切换模型订阅时，缺少不可变快照隔离，导致异步队员行为与 Prompt 适配风格严重漂移；
   - 团队缺乏 DAG 拓扑管理与人机审批预审门禁（Approve & Run），无法在开跑前审查依赖与成本。

V1.5 旨在将 OpenCode V2 的进程树绝对收敛与按需延迟代理、以及 DSH 的动态压实公式、正则 400 溢出捕获自愈、队员模型路由快照与多帧压缩持久化全面融合进 Vessel 架构。

## 2. 架构红线与禁做铁律 (绝对遵循)

1. **薄核（Thin Core）铁律**：`packages/core` 保持极致简洁，严禁将网络请求、特定 MCP 客户端或外部执行器直接写死在 core 内部。
2. **严禁调用真机 Agent**：严格遵守 `AGENTS.md` 禁做清单与任务 153 纪律，所有单元测试与回归套件必须使用内存 Mock 桩与离线仿真，严禁拉起本机真实安装的 `claude`/`codex`/`dsh`/`opencode` 进程。
3. **包管理器铁律**：严格遵守决策点 19，绝对禁止引入 `pnpm`/`bun`/`yarn` 锁文件，保持 `npm ci` 跨平台纯净可用。
4. **删除铁律**：非测试自建且位于 `os.tmpdir()` 之下的临时目录，一律走回收站，严禁任何硬删命令。
5. **Clean-room 规范**：对 OpenCode V2 与 DSH 官方源码仅作设计模式与机制级借鉴，代码与契约均遵循 Vessel 的 Behavior IR 与抽象门面，严禁直接复制粘贴第三方专有代码进生产包。
