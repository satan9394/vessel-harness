## B. 新用例的判别力 —— **通过**

新用例：`apps/cli/src/startupError.test.ts:135-150`。喂入
`settings.json 损坏（C:\Users\x\.vessel\settings.json）: Expected property name or '}' in JSON at position 1`。

**推理链（假设把 `:40` 回退成"第二个 `]` 不转义"的旧版）**

1. 旧版正则（去掉 `】\]` 中的 `\`）被解析为：类 `[.,;:)\]}>"'` + `` ` `` + `）】]` **在 `】` 后提前闭合** → 余下 `、。:：;；` 变成 6 个字面量，末尾那个 `]` 变成孤立字面量并接 `]+$`。即模式语义从"尾随标点类 + `$`"退化为"必须恰好以 `、。:：;；` 后跟一个及以上 `]` 结尾"。
2. 路径提取：`WINDOWS_PATH_RE = /[A-Za-z]:\\[^\s"']+/g`（`:34`）从 `C:\` 起贪心吃到空白前的全部，命中串 = `C:\Users\x\.vessel\settings.json）:`（以 `:` 结尾，不含任何 `]`、也不含 `、。:：;；` 序列）。
3. `trimTrailingPunctuation`（`:39-41`）用上述退化模式执行 `replace(..., '')`：待清洗串尾是 `）:`，**不满足**"`、。:：;；` + `]+$"` 的形状 → **零匹配 → 原样返回**。这正是指挥侧 E2E 实测到的"清洗实际失效"。
4. 后续 `collectPaths` 的过滤全部通过（`isWindows` 分支不再做形态过滤），`extractPath`（`:72-81`）里 `jsonLike = unique.find(p => /\.json$/i.test(p))` **落空**（结尾是 `:`）→ 回退 `unique[0]`，即带脏尾的同一串 → `res.path === 'C:\\Users\\x\\.vessel\\settings.json）:'`。
5. 断言按序执行：`:145` `kind === 'config-corrupted'` 仍**通过**（`SyntaxError` + 探针串含 `JSON`，`:106-110`）；**第一条变红的是 `:146` `expect(res.path).toMatch(/\.json$/)`**（脏尾导致不匹配）；紧接着 `:149` `line.endsWith('.json')`（该行为 `涉及文件：C:\Users\x\.vessel\settings.json）:`）**第二条变红**。
6. 修复后（当前实现）：类含 `）` 与 `:`，`...settings.json）:` → `...settings.json`，`:146` 与 `:149` 均绿。

**是否只有新用例能拦住**：是。逐条复核既有 9 例的路径命中串尾——`:37`（`...providers.json` 到串尾）、`:48`（`\\` 还原后紧接 `'`，被 `[^\s"']` 截断）、`:57`（POSIX，紧接 `'` 截断）、`:66`（紧接 `'` 截断）、`:94`（`/var/tmp/a.json` 到串尾）——**尾随字符都不是标点**，故退化版下它们仍然全绿；且既有断言多用 `toContain(WIN_JSON_PATH)`（`:44-45`），对脏尾天然免疫。→ 这条新用例是**必要且充分**的回归锁。
