## 0. 核心定位与技术愿景

Agent 领域目前存在严重的生态割裂：
- 优秀的终端 Agent（Claude Code、Codex CLI、OpenCode、DSH）各自为政，难以被其它系统直接复用；
- 试图将外部 Agent 当作子 Agent（Subagent）调起时，面临三大致命痛点：
  1. **无头交互死锁**：外部 Agent 弹出 `[y/N]` 或参数确认，因无人类交互输入而无限 Hang 住；
  2. **孤儿僵尸进程**：外部 Agent 衍生的后台编译、测试、守护子孙进程在父级退出后持续泄漏；
  3. **工作区并发污染与死锁**：多 Agent 读写主工作区，或强杀后残留 `.git/index.lock` 导致后续任务彻底瘫痪。
- Vessel 自身作为具备极强 Policy 拦截与确定性评估的 Harness，也需要标准化能力以便反向为 Claude Code、Cursor、DSH 等外部宿主提供安全可控的子 Agent 执行服务。

V1.3 的使命即是彻底攻破上述工程堡垒，构建去中心化的 **Universal Subagent Mesh**。

## 2. 核心架构契约与关键防线

### 2.1 入站网关 (Inbound)：信息隐藏与 stdio 干净通信
- **结果契约 (Result Contract)**：向外部 MCP 宿主仅返回冷冻聚合结果（`VesselTaskResultContract`：状态、产物文件、Unified Diff 摘要、Token 消耗统计），坚决不倾倒原始几十万字 Session 日志，杜绝宿主上下文爆炸。
- **协议管道纯净性**：MCP 走 stdio 传输 JSON-RPC 消息。所有 CLI 内部日志与 Policy 审计输出必须重定向至 `stderr`，严禁向 `stdout` 输出任何非 JSON-RPC 字符。

### 2.2 虚拟人类代理 (Virtual Human Proxy)：双轨制与内核沙箱
- **双轨制交互响应**：
  - 轨道一：优先映射外部 CLI 的官方非交互标志（`--print`、`-p`、`--danger-mode`）。
  - 轨道二：基于原生 Node 流的终端提示符检测（`[y/N]` / `Press Enter`），结合“连续 200ms 无新输出”双重判据消除假阳性，按 Policy 白名单毫秒级回写决策。
- **内核级进程清理**：Windows 环境下强制附加 `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`。超时或取消时瞬间抹平所有后台孙进程。
- **零 C++ 原生编译依赖**：严禁引入 `node-pty` 等破坏跨平台清洁安装的第三方库，坚守纯 TypeScript / Node。

### 2.3 出站隔离 (Outbound)：Worktree 租约与锁自愈
- **物理隔离**：外部子 Agent 必须且只能在 `os.tmpdir()` 下的精炼 Worktree 目录执行修改，父级工作区分支严禁并发直接写入。
- **锁文件自愈**：检测到 `.git/index.lock` 时，主动通过系统级 PID 探测确认持锁进程是否已终结；确认消亡后安全破锁，避免前序崩溃卡死后续任务。

### 2.4 确定性评测 (Conformance)：离线机械度量
- **自动化测试禁做红线**：严禁在未获用户显式同意的情况下，在自动化测试或 CI 中直接调用用户机器上的真实 `claude` / `codex` / `dsh` / `opencode`（遵守根 `AGENTS.md` 禁做清单与任务 153 纪律）。
- **完全走 Mock / Loopback**：自动化评测使用受控仿真桩与内部环回自测，机械验证保全度 $\ge 90\%$。
