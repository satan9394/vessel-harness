## Findings

### [P2] Red accepts mixed target and unrelated failures

`packages/policy/src/gates/redGreenGate.ts:107–110` checks that output contains an assertion marker and all configured target substrings. It does not establish that every failure belongs to the target. An honest Node test runner reporting two failures, one target assertion and one unrelated SyntaxError, receives `success: true, phase: red_verified`. This conflicts with Card196's requirement that Red fail only because of the target bug, and with card196.md's assertion that unrelated failures deny authority. This is not a forged JSON proof or arbitrary program printing fabricated assertion text.

Reproduced with a real subprocess, no files changed:

```typescript
import { RedGreenGate } from './packages/policy/src/gates/redGreenGate.ts';
const config = {
  cwd: process.cwd(),
  reproductionCommand: { executable: process.execPath, args: ['-e',
    `const test=require('node:test'); const assert=require('node:assert/strict');
     test('target regression',()=>assert.equal(0,1,'TARGET_BUG'));
     test('unrelated setup',()=>{throw new SyntaxError('UNRELATED_SETUP_FAILURE')});`] },
  fullSuiteCommand: { executable: process.execPath, args: ['-e', 'process.exit(0)'] },
  reproductionFiles: ['tasks/196-evaluator-red-green-reproduction-gate.md'],
  sourceFiles: ['tasks/197-ast-code-awareness-and-dependency-graph.md'],
  allowBaselineFailureReasons: ['TARGET_BUG'],
};
console.log(await new RedGreenGate().verifyRedPhase(config));
```

Executed via `node --import tsx --input-type=module -`. Actual exit code 1, runner summary `tests 2`, `fail 2`, target `AssertionError [ERR_ASSERTION]: TARGET_BUG`, second failure `SyntaxError: UNRELATED_SETUP_FAILURE`. Gate result: `success:true`, `phase:red_verified`.

Minimum reliable fix: replace whole-output substring admission with an evaluator-owned classification of a supported machine-readable runner report. Require at least one failed assertion, require every failed test/error to match the target predicate, and reject infrastructure errors, incomplete reports and unsupported/ambiguous formats. Vitest JSON and node:test structured events/TAP can have separate small adapters selected by the trusted evaluator. A generic fallback must deny rather than infer target-only failure from arbitrary stdout. A trusted classifier callback is also a small API option; it must remain inaccessible to generator tools and be bound to config identity. Raw exit code and output still come from the existing subprocess. Add mixed-failure and unsupported-output negative controls alongside the current target-only positive case. Merely adding a blacklist of known error strings cannot prove absence of unrelated failures.

### [P2] Recursive callers are removed from the graph

`packages/context/src/ast/symbolGraph.ts:152` drops any edge where `fromId === toId`, including a genuine recursive reference. For `export function recurse(n:number):number { return n ? recurse(n-1) : 0 }`, `getIncomingReferences('api.ts#recurse')` returns `[]`. Expected: the recurse function itself. Recursion remains a real caller when a signature changes; deleting it violates Card197's complete caller-set criterion. The bounded graph walk already tracks visited nodes, so self-edges need not be discarded to avoid traversal loops.

Minimum fix: retain self-edges for `references` (and preserve any intentionally excluded structural self-edge separately). Add a recursive-call assertion for both the service and exposed reference tool.

### [P2] Exposed get_references omits interface implementations

`packages/tools/src/ast/symbolGraphTool.ts:68–69` selects only `relation: 'references'`, while `SymbolGraphService.getIncomingReferences()` explicitly includes both references and implements. With `api.ts: export interface Contract {}` and `caller.ts: import { Contract } from './api.js'; export class Impl implements Contract {}`, the service returns `caller.ts#Impl`, but the exact graph query used by the tool returns only the interface root and no edges. An agent using get_references for a signature refactor therefore misses an implementation that the underlying service knows about.

Minimum fix: apply the same incoming relation set as getIncomingReferences, preserving requested depth and returned edge relations. Add a tool-level interface/implementer case. Alternatively explicitly define a narrower action contract, but that would need to remove the current service/tool semantic mismatch and explain how agents retrieve all signature dependents.

Graph probes (in-memory readFile, no fixture files written):

```typescript
import { SymbolGraphService } from './packages/context/src/ast/symbolGraph.ts';
const texts = new Map([
  ['api.ts', 'export function recurse(n:number):number { return n ? recurse(n-1) : 0 }; export interface Contract {}'],
  ['caller.ts', 'import { Contract } from "./api.js"; export class Impl implements Contract {}'],
]);
const graph = new SymbolGraphService({ workspaceRoot: process.cwd(),
  readFile: p => texts.get(p.replaceAll('\\', '/').split('/').at(-1)) });
await graph.indexFiles([...texts.keys()]);
console.log(await graph.getIncomingReferences('api.ts#recurse')); // actual []
console.log(await graph.getIncomingReferences('api.ts#Contract')); // actual caller.ts#Impl
console.log(await graph.getGraph('api.ts#Contract',
  { direction: 'incoming', relation: 'references', maxDepth: 1 })); // actual edges []
```
