### 2026-10-29 deep sweep · 150%/200% 的布局等价证据（协调者签收）

浏览器菜单缩放 IAB 做不了，但缩放的实质是**布局视口变小**，这一点可精确复现：1440×900 在 150% 下布局视口是 960×600，200% 下是 720×450。执行方在可见 IAB 里按这两档量了一遍，我又核了原始 JSON 与两张图：

| 档位 | innerWidth / docScrollW | 横向溢出 | 长会话标题 | 模型名 |
|---|---|---|---|---|
| 150%（960×600） | 960 / 960 | 无 | 截断（`375 > 166`） | 未截断 |
| 200%（720×450） | 720 / 720 | 无 | 截断（`375 > 166`） | 未截断 |

两条观察：① 960 宽时右侧「上下文占用 / 费用」那一列被压成竖排（每行一两个字），属「文字挤压」而不是横向溢出；② 720×450 下助手回复落在初始可视区之外，要滚动才看得到。**这两条当作布局观察记录，不作为本轮签收依据，也不新开卡**。

边界照旧写死：这是**布局等价**，不是浏览器菜单缩放；菜单缩放与 150%/200% 下的真实字形渲染、原生中文输入法仍属真机项。

### 2026-10-29 · 「原生输入法」一项撤出待办（协调者决定）

先说清楚它是什么，免得再被当成"给 harness 做输入法"：我们不做输入法，这一条是**验我们自己的 Web 输入框别被用户的中文输入法搞坏**——组词过程中的 Enter / 229 事件不能顺手把消息发出去。TUI 类前端（opencode 的主界面）看不到组词，那是终端的事；我们有自己的 React textarea，所以这块归我们。

**判定：撤出待办，按"代码守卫 + 单测"记档。** 依据：

1. 守卫与 opencode 同款：`e.isComposing || e.keyCode === 229`。我们这边在 `ConversationView.tsx:418`、`TaskComposer.tsx:109`、`ModelChips.tsx:67`、`ModelQuickSwitcher.tsx:43` 都有，palette 与 message-list 的快捷键也排除了组词态。没有可抄的增量。
2. 单测已经覆盖组词态：`TaskComposer.test.tsx`、`ConversationView.interaction.test.tsx`、`ModelChips.test.tsx` 手工触发 `compositionstart/update/end` 并断言 `keyCode: 229` 与 `isComposing: true` 两种变体都不发送。
3. 用户盘上另有一份更狠的实现 `cc-switch/src/components/ui/ime-safe-input.tsx`，但它治的是**另一个**病：受控输入在组词途中被父组件重写导致候选串被冲掉，以及 WebKit 在 `compositionend` 后补发 input 造成重复提交。我们的 `value={input}` 只由该 textarea 自己的 `onChange` 写入，组词期间没有外部写入，这个病在我们这儿不成立。真遇到丢字/重复再按它那套改。
4. 这一条不是产品风险，是「一次性的手测」。它已经在日常使用里天天被触发——真有病，用户当天就会发现，不值得占一个验收位。

顺带纠正一条我此前的错误表述：候选词的选择是鼠标点击或数字键，Enter 在微软拼音下提交的是什么取决于输入法设置（有的提交原始字母，有的确认首选），**不能把它当通则**。所以判据只能是"组词态一律不发送"，而不是"Enter 应该上屏什么"——这也正是 `keyCode === 229` 那个守卫存在的原因。
